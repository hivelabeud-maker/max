# MECE · 이슈트리

`rfp-analyst`가 과업을 4분류(명시·숨은·미정의·위험)한 다음, 조사·제안 구조를 짜는 단계에서 쓴다.
결과는 `pyramid-principle`로 넘겨 목차가 된다.

MECE는 두 가지만 본다.
- **겹침 없음** — 두 항목이 같은 것을 다르게 부르고 있지 않은가. 담당이 애매해지는가
- **빠짐 없음** — 정한 범위 안에서 중요한 부분을 다 덮는가

MECE는 규율이지 구호다. 현실을 억지로 반듯하게 만들려고 쓰면 신호가 죽는다.

## 언제 쓰나
- RFP 과업이 증상·원인·요구·액션으로 뒤섞여 있을 때
- 조사 항목이 20개인데 우선순위가 없을 때
- 제안 목차의 2장과 4장이 같은 얘기를 하고 있을 때
- 경쟁사 분류·타깃 세그먼트 축을 정할 때

## 언제 안 쓰나
- 아직 아이디어를 쏟아내는 중일 때 — 구조가 이르면 약한 신호가 묻힌다 → `brainstormer`
- 인과를 증명해야 할 때 — 이슈트리는 무엇을 볼지 정하지 인과를 증명하지 않는다
- 결정 질문·범위·담당이 아직 없을 때

## 필요 입력
핵심 질문 / 범위 경계 / 제약(예산·기간·인력) / 결정 시점 / 지금 가진 근거

빠진 입력은 멈추지 말고 `미확인`으로 표시하고, 쓴 가정을 적고, 확인 액션을 붙인다.

## 절차

### 1. 핵심 질문 하나
분석이 답해야 할 질문을 한 문장으로. 결정에 쓰이는 질문이어야 한다.

### 2. 1단 가지 나누기
답의 공간을 덮는 큰 가지를 만든다. 흔한 축 네 가지:
- 구조 축 — 요소를 물리적으로 쪼갠다 (매출 = 유입 × 전환 × 객단가)
- 프로세스 축 — 시간 순서로 쪼갠다 (인지 → 관심 → 구매 → 재구매)
- 대상 축 — 누구를 기준으로 쪼갠다 (신규/기존, B2B/B2C)
- 이분 축 — 예/아니오로 쪼갠다. 빠짐이 구조적으로 없다

한 단계 안에서는 축 하나만 쓴다. 축을 섞으면 반드시 겹친다.

### 3. 가지를 답할 수 있는 질문까지 내린다
잎(leaf)은 "조사하면 답이 나오는" 크기여야 한다. "브랜드가 약하다"는 잎이 아니다. "20대 비보조 인지도가 경쟁사 대비 몇 %인가"가 잎이다.

### 4. 겹침·빠짐 감사
| 점검 | 방법 |
|---|---|
| 겹침 | 두 가지를 나란히 놓고 같은 사례가 양쪽에 들어가는지 본다 |
| 레벨 혼동 | 상위 개념과 하위 사례가 같은 층에 있는지 본다 |
| 빠짐 | "이 밖에 결론을 바꿀 수 있는 게 있나"를 묻는다. 있으면 가지를 추가하거나 범위 밖으로 명시한다 |
| 잔여함 | 어쩔 수 없이 남는 건 "기타"로 두되 비중을 적는다. 기타가 30%를 넘으면 축이 틀렸다 |

### 5. 가설트리로 전환(선택)
잎마다 "아마 이럴 것이다"를 붙이면 가설트리가 된다. 가설에는 **반증 테스트**를 같이 적는다. 무엇을 보면 이 가설이 틀렸다고 인정할 것인가.

### 6. 우선순위
결론을 바꿀 확률 × 조사 비용으로 순서를 정한다. 답이 뻔한 가지는 뒤로 민다.

## 출력 템플릿

```markdown
## 핵심 질문
질문:
결정 용도:
범위(포함 / 제외):
제약:

## 이슈트리
| 1단 가지 | 하위 질문 | 왜 중요한가 | MECE 메모 |
|---|---|---|---|
|  |  |  |  |

축: {구조 / 프로세스 / 대상 / 이분}

## 가설과 반증 테스트
| 잎 질문 | 가설 | 틀렸다고 볼 신호 | 확인 방법 |
|---|---|---|---|
|  |  |  |  |

## 근거 계획
| 잎 질문 | 필요한 근거 | 출처 후보 | 티어 | 담당 |
|---|---|---|---|---|
|  |  |  |  |  |

## 조사 순서
| 순위 | 항목 | 이유 | 결론 영향도 |
|---|---|---|---|

## 미확인
- 가정:
- 확인 액션·시점:
```

## 품질 게이트
- 한 층 안에서 축이 하나인가
- 잎이 조사 가능한 크기인가
- 기타 비중이 30% 아래인가
- 결론을 바꿀 가지를 앞에 뒀는가
