# UX 오딧 (현행 서비스 진단)

리뉴얼·개선 제안에서 "왜 바꿔야 하는가"를 만드는 챕터다. `marketer` 외부 조사(시장·경쟁)가 밖을 보는 것이라면, 이건 클라이언트 서비스 안을 본다.
결과는 `insight-derivation`으로 넘겨 인사이트가 되고, `pyramid-principle`로 목차가 된다.

핵심은 세 가지.
1. **지표를 먼저 고정한다.** 눈에 띄는 것부터 지적하면 취향 싸움이 된다
2. **화면에 번호를 찍는다.** 문제를 실제 스크린샷 위에 고정하면 반박이 어려워진다
3. **지표를 그룹으로 묶는다.** 8개 지적은 잔소리, 4개 그룹은 전략이다

## 8개 지표 (기본형)
서비스 성격에 따라 갈아끼우되, **먼저 확정하고 시작한다.** 진단 중에 지표를 바꾸면 결과가 자의적이 된다.

| # | 지표 | 평가 질문 |
|---|---|---|
| 01 | Landing / 진입 | 원하는 정보에 빠르게 닿도록 필요한 메뉴·기능을 우선 배치했는가 |
| 02 | Personalized Experience | 로그인 후 사용자 상태에 맞춘 화면을 주는가 |
| 03 | Onboarding Flow | 첫 진입부터 가입 완료까지 불필요한 단계·이탈 요소 없이 이어지는가 |
| 04 | Search / 탐색 | 최소한의 키워드로 원하는 정보에 정확히 도달하는가 |
| 05 | Customer Support | 이용 중 생긴 문제를 즉시 해결할 접점이 있는가 |
| 06 | Mobile Optimization | 모바일에서 조작 편의성과 가독성이 확보됐는가 |
| 07 | Labeling | 메뉴·버튼 명칭이 직관적이고 서비스 전반에 걸쳐 일관된 용어를 쓰는가 |
| 08 | Error | 정보·기능이 오류 없이 제공되는가 |

이커머스면 04에 비교·결제를, 게임이면 튜토리얼·재화 구조를 넣는 식으로 조정한다.

## 지표별 진단 장표 구조
지표 하나가 한 장이다.

```
좌측 (30%)                     우측 (70%)
─────────────────────────      ────────────────────────────
Analysis 0N                    실제 화면 캡처 2~3컷
{지표명}                        캡처 위에 ①②③ 번호 마킹
[UX Audit Checklist] 뱃지       (문제 지점에 정확히)
{평가 질문 한 줄}

[판정 라벨]
{판정 요약 한 줄}

1. {문제 진술 + 그로 인한 결과}
2. {문제 진술 + 그로 인한 결과}
```

**판정 라벨은 3단계로 고정한다.**
- `Good` — 유지. 잘 된 것도 표시해야 진단이 공정해 보인다
- `Need Improvement` — 개선 대상
- `Critical` — 이탈·매출에 직접 닿는 문제

문제 진술은 현상만 쓰지 않고 결과까지 붙인다. "검색 결과가 정확하지 않다" ✗ / "질문 의도와 다른 답변이 나와 외부 페이지로 이동해야 하고, 추가 탐색 부담이 생긴다" ✓

## 인사이트 묶기
8개 지표 진단이 끝나면 **비슷한 뿌리끼리 3~5개 그룹으로 묶는다.** 그룹 이름은 문제 영역으로 쓴다.

예: Discovery & Navigation (01·04·07) / Personalized & Adaptive (02) / Onboarding & Exit (03) / Usability & Support (05·06·08)

그룹마다 Issue → Approach 한 줄씩.

| 그룹 | Issue (지금 벌어지는 일 + 사용자에게 생기는 결과) | Approach (무엇을 도입·재설계할 것인가) |
|---|---|---|
| Discovery & Navigation | 서비스 구조 중심 배치와 키워드 기반 검색으로 반복 탐색이 필요해 초기 탐색 피로 발생 | Top Task 기반 IA 재설계, 검색·추천·요약 통합, 목적 기반 CTA |

이 표가 제안 챕터의 목차가 된다. Approach 한 칸이 제안서 한 챕터로 펴진다.

## 절차
1. 대상 화면 범위를 정한다 (핵심 여정 1~2개. 전 화면을 보려 하면 진단이 얕아진다)
2. 지표 8개를 확정한다
3. 지표별로 실제 화면을 캡처하고 문제 지점에 번호를 찍는다
4. 판정 라벨을 단다. Good이 하나도 없으면 진단이 편향됐는지 다시 본다
5. 문제 진술을 "현상 + 결과" 형태로 쓴다
6. 그룹으로 묶고 Issue → Approach 표를 만든다
7. `insight-derivation`으로 넘겨 외부 조사 결과와 충돌하는 지점을 찾는다

## 출력 템플릿

```markdown
## 진단 범위
대상 화면: / 여정: / 기기: / 진단일:

## 지표별 진단
### Analysis 01. {지표명}
- 평가 질문:
- 판정: Good / Need Improvement / Critical
- 판정 요약:
- 문제 1: {현상} → {사용자에게 생기는 결과}
- 문제 2:
- 근거 화면: {캡처 파일명 + 마킹 번호}

## 인사이트 그룹
| 그룹 | 포함 지표 | Issue | Approach |
|---|---|---|---|

## 제안 연결
| Approach | 제안서 챕터 | 예상 공수 |
|---|---|---|
```

## 품질 게이트
- 지표를 진단 시작 전에 확정했는가
- 문제마다 실제 화면 근거가 있는가
- 문제 진술에 결과가 붙었는가
- Good 판정이 하나도 없는가 (전부 나쁘다는 진단은 신뢰를 잃는다)
- 그룹 수가 3~5개인가 (8개 그대로 가면 전략이 안 된다)
- Approach가 제안서 챕터로 이어지는가

> 참고: SK broadband B world Renewal Proposal(HIVELAB, 2026.04) 덱의 Analysis 챕터 구조.
